By the end of this page you'll have a live inbox and a confirmed send to receive to reply loop, using the same four objects you'll reach for in every later workflow: the inbox, the message, the thread, and the reply.

Everything below runs against one base URL and one auth header. Here they are up front so every snippet on the page is self-contained:

```bash
# Base URL for every request
https://api.agentmail.to/v0

# Auth header for every request
Authorization: Bearer <API_KEY>
```

## Before you begin

You need two things:

1. **An account and an API key.** The key is what goes in the `Authorization` header. Treat it like a password: read it from an environment variable in real code, and never commit it.
2. **The two constants above.** Every request in this tutorial targets the base URL `https://api.agentmail.to/v0` and carries `Authorization: Bearer <API_KEY>`. If either is missing or wrong, calls fail before they reach any real logic.

If you don't have an account yet, start with the [Introduction](./introduction) and come back here once you have a key. For how the pieces fit together, see [Architecture](./architecture).

Export your key and the base URL so the snippets below can reference them:

```bash
export AGENTMAIL_API_KEY="<API_KEY>"
export AGENTMAIL_BASE_URL="https://api.agentmail.to/v0"
```

## Install and authenticate

You can drive the whole tutorial with the Python SDK, the TypeScript SDK, the CLI, or raw `curl`. The SDKs are how most integrations ship; the CLI is handy for poking at the API from a terminal, and `curl` works anywhere with no install. Choose one and use it for every step; all four hit the same endpoints and the same base URL.

The SDK clients take the key as a constructor argument, and the CLI reads it from the `AGENTMAIL_API_KEY` environment variable you exported above, so there's no separate login step in any lane. To confirm the key is accepted, every lane calls `GET /v0/auth/me`, which returns the scope your key resolves to.

<CodeGroup>

```python Python
# Install the SDK: pip install agentmail
import os

from agentmail import AgentMail

client = AgentMail(api_key=os.environ["AGENTMAIL_API_KEY"])

# Confirm the key is accepted; prints the caller scope
print(client.auth.me())
```

```typescript TypeScript
// Install the SDK: npm install agentmail
import { AgentMailClient } from "agentmail";

const client = new AgentMailClient({ apiKey: process.env.AGENTMAIL_API_KEY });

// Confirm the key is accepted; prints the caller scope
console.log(await client.auth.me());
```

```bash CLI
# Install the CLI (Node.js required)
npm install -g agentmail-cli

# Confirm the key is accepted; prints the caller scope
agentmail auth me
```

```bash curl
# No install needed. Every call sets the header and base URL explicitly.
# Confirm the key is accepted:
curl "$AGENTMAIL_BASE_URL/auth/me" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY"
```

</CodeGroup>

For an organization-scoped API key, a successful response looks like this (`scope_id` equals the id of whatever tier the key is bound to, here the organization):

```json Sample response
{
  "scope_type": "organization",
  "scope_id": "<organization_id>",
  "organization_id": "<organization_id>",
  "api_key_id": "<api_key_id>"
}
```

Read the response by status code (the SDKs raise an error instead of returning one, with the same codes attached):

- **`200`** — your key works. The body describes the scope this key is allowed to act on.
- **`401`** — the key is missing or wrong. Re-check `AGENTMAIL_API_KEY`.
- **`404`** — the base URL is off, almost always a missing `/v0` segment. See [Common mistakes](#common-mistakes).

## Create an inbox

An **inbox** is the mailbox you send to and receive from. It has an address-like id that other senders (including you, in the next step) can deliver to. Creating one is your first authenticated write.

The request body is all-optional. The simplest call sends `{}`; passing a `display_name` just makes the inbox easier to recognize later.

<CodeGroup>

```python Python
inbox = client.inboxes.create(display_name="Quickstart inbox")

print(inbox.inbox_id)
```

```typescript TypeScript
const inbox = await client.inboxes.create({ displayName: "Quickstart inbox" });

console.log(inbox.inboxId);
```

```bash CLI
agentmail inboxes create \
  --display-name "Quickstart inbox"
```

```bash curl
curl -X POST "$AGENTMAIL_BASE_URL/inboxes" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "display_name": "Quickstart inbox"
  }'
```

</CodeGroup>

The response is the inbox object. Because you didn't pass a `username`, one is generated for you, on the default `agentmail.to` domain:

```json Sample response
{
  "pod_id": "<pod_id>",
  "inbox_id": "<generated-username>@agentmail.to",
  "email": "<generated-username>@agentmail.to",
  "display_name": "Quickstart inbox",
  "created_at": "2026-07-13T09:15:04Z",
  "updated_at": "2026-07-13T09:15:04Z"
}
```

The field you need right now is `inbox_id`: it is the inbox's email address, it is what you send to in the next step, and it goes in the path of every later call. Copy it and keep it handy.

## Send a test email to the inbox

Now give the inbox something to receive. Send a **message** addressed to the `inbox_id` you just created, so the loop closes back to you. A message is a single email: it has one or more recipients (`to`), a `subject`, and content in `text` (and/or `html`).

Note the field is `text`, not `body`. The send endpoint takes the inbox id in the path: `/v0/inboxes/{inbox_id}/messages/send`.

<CodeGroup>

```python Python
sent = client.inboxes.messages.send(
    inbox_id="<inbox_id from the previous step>",
    to="<inbox_id from the previous step>",
    subject="Hello from the quickstart",
    text="This is a test message.",
)

print(sent.message_id, sent.thread_id)
```

```typescript TypeScript
const sent = await client.inboxes.messages.send(
  "<inbox_id from the previous step>",
  {
    to: "<inbox_id from the previous step>",
    subject: "Hello from the quickstart",
    text: "This is a test message.",
  },
);

console.log(sent.messageId, sent.threadId);
```

```bash CLI
agentmail inboxes:messages send \
  --inbox-id "<inbox_id from the previous step>" \
  --to "<inbox_id from the previous step>" \
  --subject "Hello from the quickstart" \
  --text "This is a test message."
```

```bash curl
curl -X POST "$AGENTMAIL_BASE_URL/inboxes/<inbox_id>/messages/send" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "to": "<inbox_id from the previous step>",
    "subject": "Hello from the quickstart",
    "text": "This is a test message."
  }'
```

</CodeGroup>

The response is small on purpose: the id of the message you just sent, and the id of the new thread it started.

```json Sample response
{
  "message_id": "<message_id>",
  "thread_id": "<thread_id>"
}
```

Delivery is not always instant. Give it a moment before you try to read it in the next step.

## Fetch the received message

List the messages on your inbox to find the one that just arrived.

<CodeGroup>

```python Python
messages = client.inboxes.messages.list(inbox_id="<inbox_id from step 3>")

for message in messages.messages:
    print(message.message_id, message.thread_id, message.subject)
```

```typescript TypeScript
const messages = await client.inboxes.messages.list("<inbox_id from step 3>");

for (const message of messages.messages) {
  console.log(message.messageId, message.threadId, message.subject);
}
```

```bash CLI
agentmail inboxes:messages list \
  --inbox-id "<inbox_id from step 3>"
```

```bash curl
curl "$AGENTMAIL_BASE_URL/inboxes/<inbox_id>/messages" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY"
```

</CodeGroup>

The response is a page of message summaries, newest first. Fields you didn't set (`cc`, `bcc`, `attachments`) are simply absent, and a `next_page_token` appears only when there are more pages:

```json Sample response
{
  "count": 1,
  "messages": [
    {
      "inbox_id": "<your inbox_id>",
      "thread_id": "<thread_id>",
      "message_id": "<message_id>",
      "labels": ["received"],
      "timestamp": "2026-07-13T09:16:11Z",
      "from": "<your inbox_id>",
      "to": ["<your inbox_id>"],
      "subject": "Hello from the quickstart",
      "preview": "This is a test message.",
      "size": 1024,
      "created_at": "2026-07-13T09:16:11Z",
      "updated_at": "2026-07-13T09:16:11Z"
    }
  ]
}
```

In the response, find the test message you sent. Two values from it matter for the reply:

- **`message_id`** — the id of the message itself, which confirms the send to receive half of the loop worked. This is what you reply on next.
- **`thread_id`** — the conversation the message belongs to. Your reply lands on this same thread.

## Reply and confirm it landed

Send a **reply** on the message you just found. In AgentMail a reply targets a message id, not a thread id: `POST /v0/inboxes/{inbox_id}/messages/{message_id}/reply`. The reply is attached to the same thread as the original, so the conversation stays together. Its body uses `text` (and/or `html`).

<Note>
A message id is an RFC 822 id, angle brackets and all: `<0100...@email.amazonses.com>`. The SDKs and CLI take it as-is, but in the curl lane it goes into the URL path, so URL-encode it first (`<` → `%3C`, `>` → `%3E`, `@` → `%40`). Pasted raw, the request never matches the route.
</Note>

<CodeGroup>

```python Python
reply = client.inboxes.messages.reply(
    inbox_id="<inbox_id from step 3>",
    message_id="<message_id from the previous step>",
    text="Got it, replying from the quickstart.",
)

print(reply.message_id, reply.thread_id)
```

```typescript TypeScript
const reply = await client.inboxes.messages.reply(
  "<inbox_id from step 3>",
  "<message_id from the previous step>",
  { text: "Got it, replying from the quickstart." },
);

console.log(reply.messageId, reply.threadId);
```

```bash CLI
agentmail inboxes:messages reply \
  --inbox-id "<inbox_id from step 3>" \
  --message-id "<message_id from the previous step>" \
  --text "Got it, replying from the quickstart."
```

```bash curl
curl -X POST "$AGENTMAIL_BASE_URL/inboxes/<inbox_id>/messages/<url-encoded message_id>/reply" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "text": "Got it, replying from the quickstart."
  }'
```

</CodeGroup>

The response has the same shape as the send response above: a new `message_id` for the reply, and the same `thread_id` as the original message.

To confirm the reply landed, list the messages the same way you did in the previous step. You should now see two messages sharing one `thread_id`: your original test email and the reply you just sent. When both show up, the full send to receive to reply loop is working end to end.

You can also confirm it visually: open your inbox in the [console](https://console.agentmail.to) and the loop is sitting there as one thread — the test message and the reply together, labeled `Sent`, `Received`, and `Unread`.

## What just happened

You touched four objects. This is the mental model to carry into the rest of the docs:

- **Inbox**: a mailbox with an address-like `inbox_id`. It sends and receives mail. You created one in step 3.
- **Message**: a single email with recipients, a subject, and `text`/`html` content. You sent one to your inbox and then read it back.
- **Thread**: the conversation a message belongs to, tracked by `thread_id`. It groups an original message with its replies so a back-and-forth stays together.
- **Reply**: a new message attached to an existing message's thread rather than a fresh conversation. Some flows build a reply as a **draft** first and then send it; the end result is the same message on the thread. Your reply landed on the same `thread_id` as the test email.

## Common mistakes

**Omitting `/v0` from the base URL.**
Symptom: requests return `404 Not Found` even though your key is valid and the rest of the path looks right.
Fix: make sure the base URL is exactly `https://api.agentmail.to/v0`, including the `/v0` version segment, on every request. A base URL of `https://api.agentmail.to` without `/v0` will not resolve to the API.

**Re-running signup when an account already exists.**
Symptom: signing up again returns a conflict instead of a fresh account, and you don't get a clean new key.
Fix: don't re-run signup to recover. If you already have an account, sign in and reuse or rotate your existing API key instead. See the [Introduction](./introduction) for where to find and manage your key.

**Run a send-receive-reply loop against the AgentMail API**

Creates an inbox, sends a test message to it, lists received messages, and replies on the same thread. Use this to verify an API key end to end and to learn the core object model: inbox, message, thread, reply.

## No API key yet? Sign up in one call — FIRST TIME ONLY

If you already have an `AGENTMAIL_API_KEY`, SKIP this section entirely — never re-run sign-up to "start fresh"; it does not create a new account.

```bash
# One-time agent sign-up: creates an org, an inbox, and an API key.
# human_email = the email of the human you work for (they receive an OTP).
curl -X POST "https://api.agentmail.to/v0/agent/sign-up" \
  -H "Content-Type: application/json" \
  -d '{"human_email": "<your human'"'"'s email>", "username": "<desired inbox username>"}'
# response: { "organization_id", "inbox_id", "api_key", "instructions" }
# The api_key is shown ONCE — export it immediately.

# After your human reads the 6-digit OTP from their email, lift restrictions:
curl -X POST "https://api.agentmail.to/v0/agent/verify" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"otp_code": "<6-digit code>"}'
```

Until verified, the account is restricted: 1 inbox, 10 sends/day, and sending is allow-listed to `human_email` only — so send your first message to your human asking them for the OTP code. If sign-up returns 403 `AlreadyExistsError`, an account for that email already exists: STOP, do not retry with variations; use the existing key, or ask your human to retrieve one from https://console.agentmail.to.

## Do this

```bash
export AGENTMAIL_API_KEY="<API_KEY>"
BASE="https://api.agentmail.to/v0"

# 1. Verify the credential
curl "$BASE/auth/me" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY"

# 2. Create an inbox (body optional; display_name recommended)
curl -X POST "$BASE/inboxes" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"display_name": "Quickstart inbox"}'
# response includes: inbox_id (the inbox's email address), created_at

# 3. Send a message to the inbox itself (content field is "text", not "body")
curl -X POST "$BASE/inboxes/<inbox_id>/messages/send" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"to": "<inbox_id>", "subject": "Hello", "text": "Test message"}'
# response: { "message_id": "...", "thread_id": "..." }

# 4. List received messages (delivery may take a moment; retry if empty)
curl "$BASE/inboxes/<inbox_id>/messages" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY"

# 5. Reply to the message id (NOT the thread id).
# The id is an RFC 822 id with < > @ characters: URL-encode it in the path.
curl -X POST "$BASE/inboxes/<inbox_id>/messages/<message_id>/reply" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text": "Reply body"}'
# response: new message_id, same thread_id
```

## Facts

- Base URL is `https://api.agentmail.to/v0`. The `/v0` segment is required; `https://api.agentmail.to` without `/v0` returns 404.
- Every request carries the header `Authorization: Bearer <API_KEY>`.
- `GET /v0/auth/me` returns the scope the authenticated key resolves to. Status 200 means the key is valid.
- `POST /v0/inboxes` creates an inbox. The request body is optional and all fields in it are optional; `{}` is a valid body.
- The `inbox_id` returned by `POST /v0/inboxes` is the inbox's email address, formed as `username@domain`; username is randomly generated unless specified, domain defaults to `agentmail.to`.
- The `inbox_id` goes in the path of every message call: `/v0/inboxes/{inbox_id}/messages`, `/v0/inboxes/{inbox_id}/messages/send`, `/v0/inboxes/{inbox_id}/messages/{message_id}/reply`.
- `POST /v0/inboxes/{inbox_id}/messages/send` accepts `to`, `subject`, and content in `text` and/or `html`. The content field is `text`, never `body`.
- `POST /v0/inboxes/{inbox_id}/messages/send` returns `message_id` and `thread_id`.
- Delivery into the recipient inbox is not instant; poll `GET /v0/inboxes/{inbox_id}/messages` until the message appears.
- `GET /v0/inboxes/{inbox_id}/messages` returns `count`, `limit`, `next_page_token`, and a `messages` array; `next_page_token` paginates.
- Each item in the `messages` array of `GET /v0/inboxes/{inbox_id}/messages` includes `message_id`, `thread_id`, `from`, `to`, `subject`, `preview`, and `timestamp`.
- `POST /v0/inboxes/{inbox_id}/messages/{message_id}/reply` accepts content in `text` and/or `html` and returns a new `message_id` with the same `thread_id` as the original message.
- Message ids are RFC 822 ids (like `<0100...@email.amazonses.com>`), angle brackets included. URL-encode them wherever they appear in a URL path (`<` -> `%3C`, `>` -> `%3E`, `@` -> `%40`). The SDKs and CLI accept them raw.
- A reply always lands on the same `thread_id` as the message it replies to; an original message and its replies share one `thread_id`.
- Some flows build a reply as a draft first and then send it; the result is the same message on the thread.
- The CLI is installed with `npm install -g agentmail-cli` (Node.js required) and reads the key from the `AGENTMAIL_API_KEY` environment variable; there is no separate login step.
- CLI command equivalents: `agentmail auth me`, `agentmail inboxes create`, `agentmail inboxes:messages send`, `agentmail inboxes:messages list`, `agentmail inboxes:messages reply`.
- `POST /v0/agent/sign-up` takes `{ human_email, username }` (both required) and returns `organization_id`, `inbox_id` (formed as `username@agentmail.to`), a one-time-visible `api_key`, and `instructions`. It needs no auth header. A 6-digit OTP is emailed to `human_email`.
- Sign-up is first-time-only per `human_email`. Re-calling it for a NOT-yet-verified account does not error: it rotates the API key (invalidating the one you had) and re-sends the OTP if expired. Re-calling it for a verified or human-registered email returns 403 `AlreadyExistsError`.
- `POST /v0/agent/verify` takes `{ otp_code }` (6 digits) with the `Authorization: Bearer` header and lifts the sign-up restrictions. Wrong codes are limited to a few attempts; an expired OTP requires re-running sign-up.
- Until verified, an agent-signed-up account has 1 inbox, 10 sends/day, and can send only to its `human_email`.

## Not supported

- Replying by thread id: there is no reply endpoint that takes a `thread_id`. Replies target a message id via `POST /v0/inboxes/{inbox_id}/messages/{message_id}/reply`.
- A `body` field in send or reply requests: message content goes in `text` and/or `html`.
- Serving the API at `https://api.agentmail.to` without the `/v0` prefix: those requests return 404.
- Re-running sign-up to get a fresh account, a clean slate, or a second account for the same `human_email`: there is exactly one account per email. Against a verified account it returns 403 `AlreadyExistsError`; against an unverified one it silently rotates the key you already exported, breaking it.
- Sending to anyone other than `human_email` before `POST /v0/agent/verify` succeeds: blocked by the sign-up allowlist.

## Errors

| Error | HTTP | Cause | Fix |
|---|---|---|---|
| Unauthorized | 401 | `AGENTMAIL_API_KEY` missing or wrong in the `Authorization: Bearer` header | Re-check the key value and the header |
| Not Found | 404 | Base URL missing the `/v0` segment, or a wrong path | Use exactly `https://api.agentmail.to/v0` |
| `AlreadyExistsError` | 403 | Re-running sign-up when a verified account for that email already exists | STOP retrying sign-up. Use the key you already have, or have your human get one from https://console.agentmail.to |
| `ForbiddenError` (wrong code / OTP expired) | 403 | Bad or expired `otp_code` on `POST /v0/agent/verify` | Re-check the code with your human; if expired, re-run sign-up to get a fresh OTP (this rotates the key) |

## Verify

```bash
curl "https://api.agentmail.to/v0/auth/me" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY"
```

Status 200 with a JSON body describing the key's scope confirms the credential. To confirm the full loop, run `GET /v0/inboxes/{inbox_id}/messages` and check that two messages (the original and the reply) share one `thread_id`.
