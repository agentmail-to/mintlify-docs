Before you work through the task pages, it helps to see how AgentMail's objects fit together. This page names each primitive, shows how they contain each other, and explains the one rule that trips people up: whether a call needs a pod in the path depends on the scope of the API key you are using. If you have not set up a key yet, start with the [Introduction](/introduction) and then the [Quickstart](/quickstart).

## The big picture

AgentMail nests from your account down to individual messages. An organization holds one or more pods, each pod holds inboxes, and each inbox owns the messages, threads, and drafts that flow through its email address. Everything else (domains, keys, webhooks, labels, lists) hangs off one of these levels.

## Organization

The organization is your account: the top of the tree and the tenant that everything else belongs to. When you sign up, you get an organization. Every pod, inbox, and message you create lives somewhere underneath it. Request paths never include an organization segment; your key implies which organization you are working in.

## Pod

A pod is a sub-organization inside your organization, and it is the unit of multi-tenancy: if you are building a product where each of your customers needs their own isolated set of inboxes, you give each customer a pod. Inboxes, and the messages under them, are partitioned by pod, so one tenant's mail never mixes with another's.

Because the pod is the tenancy boundary, it is also the level your API key scope is usually anchored to.

## Inbox

An inbox is an email address, and it owns the mail that passes through it. Every message, thread, and draft belongs to exactly one inbox. When you send or receive email, you are always doing so as a specific inbox. Create an inbox under a pod, and that inbox is the addressable unit you read from and write to for the rest of its life.

## The other primitives

Everything below is a supporting object that hangs off one of the three levels above. Most of them attach at whichever level you create them, which is exactly why your key's scope matters.

| Primitive | What it is | What it belongs to |
| --- | --- | --- |
| Domain | A sending/receiving domain you own and verify | Pod |
| API key | A credential that carries a scope | Organization, pod, or inbox |
| Webhook | An HTTP endpoint AgentMail calls on events | Organization, pod, or inbox |
| WebSocket | A live connection for streaming events; subscribes to inboxes within the key's reach | The level your key is scoped to |
| Message | A single email | Inbox |
| Thread | A grouped conversation of related messages | Inbox |
| Draft | An unsent message | Inbox |
| Label | A tag on messages and threads; system labels (sent, received, bounced) are managed by AgentMail | Inbox |
| List | An allow or block list of addresses or domains, per direction (send, receive, reply) | Organization, pod, or inbox |

## How key scope flows

Every request goes to the base URL `https://api.agentmail.to/v0` with your key in an `Authorization: Bearer <key>` header. An API key carries a scope, and that scope determines whether you name a pod in the path.

- A **pod-scoped key** is tied to one pod. It resolves its scope on its own, so you do not name the pod in the request path. AgentMail already knows which pod the key belongs to. Inbox-scoped keys work the same way, one level down.
- An **org-scoped key** can reach any pod in your organization. Because it is not tied to one, it cannot resolve scope on its own, so you must name the pod in the request path for calls that operate on pod-level resources, for example `/v0/pods/{pod_id}/inboxes`.

The contrast in one table:

| Key scope | Does the path name a pod? |
| --- | --- |
| Pod-scoped | No. Scope resolves from the key. |
| Org-scoped | Yes. You name the target pod in the path. |

Practically: if your code was written against a pod-scoped key and you swap in an org-scoped key, calls that used to work will start failing until you add the pod to the path (and the other way around). Knowing your key's scope up front saves that debugging round.

## Verify a key's scope

When you are not sure what a key can reach, ask AgentMail directly: call `GET /v0/auth/me` with the key in question, and the response tells you what that key is scoped to.

```bash
curl https://api.agentmail.to/v0/auth/me \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY"
```

The response is the caller's scope. These are the fields to read:

- **`scope_type`**: the level this key is anchored to. One of `organization`, `pod`, or `inbox`. This is the field that answers the pod-in-path question: an `organization` key names the pod in the path, a `pod` (or `inbox`) key resolves it from the key.
- **`scope_id`**: the id of the thing named by `scope_type`. For a pod-scoped key it is the pod id, for an org-scoped key it is the organization id, for an inbox-scoped key it is the inbox id.
- **`organization_id`**: the organization the key belongs to, always present regardless of scope.
- **`pod_id`**: present when the key resolves to a specific pod, that is, when `scope_type` is `pod` or `inbox`. This is the pod you would otherwise have to name in the path, so an org-scoped key will not have it.
- **`inbox_id`**: present when the key is scoped down to a single inbox (an email address).
- **`api_key_id`**: the id of the key itself. Present only when the caller authenticated with an API key; absent for JWT and proxy credentials.

Read `scope_type` first: it tells you whether the task pages' calls need a pod segment. If it comes back `organization`, include the pod in your paths; if it comes back `pod` or `inbox`, leave the pod segment out and let the key resolve it.
