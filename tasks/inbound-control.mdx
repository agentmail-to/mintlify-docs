---
title: Control who can email your agent
description: Use allow and block lists to decide which senders reach your agent's inbox and which recipients it can email.
---

An agent inbox with no filter answers anyone, including spammers, phishers, and other bots. Lists put a policy in front of both directions: who can email your agent, and who your agent can email. A list entry is either a full address (`partner@example.com`) or a whole domain (`example.com`), and every list is identified by two dimensions: a **direction** (`send`, `receive`, or `reply`) and a **type** (`allow` or `block`).

## The six lists

| List | What it does |
| --- | --- |
| `receive` / `allow` | Only accept new inbound mail from these addresses or domains |
| `receive` / `block` | Block new inbound mail from these addresses or domains |
| `send` / `allow` | Only send to these addresses or domains |
| `send` / `block` | Refuse sends to these addresses or domains |
| `reply` / `allow` | Only accept replies from these addresses or domains |
| `reply` / `block` | Block replies from these addresses or domains |

`receive` and `reply` are separate branches of the inbound path. When mail arrives, AgentMail resolves its `In-Reply-To` header against the inbox's existing threads. If the message answers something your inbox sent, only the `reply` lists are checked and the `receive` lists are skipped; if it starts a new thread, only the `receive` lists are checked. This split matters for agents that initiate outbound mail: you can lock `receive` down to your own domain while leaving `reply` lists empty, so responses to the agent's own messages still come through.

## Scopes cascade from inbox to pod to org

Each of the six lists exists at three scopes, and evaluation walks from the most specific to the broadest:

1. **Inbox** (`/inboxes/{inbox_id}/lists/...`) is checked first.
2. **Pod** (`/pods/{pod_id}/lists/...`) is checked next.
3. **Organization** (`/lists/...`) is checked last.

The first match wins and stops the cascade. Within each scope, an exact address match is checked before a domain match, and at each of those an `allow` match is checked before a `block` match. So an inbox-level allow entry for `alice@example.com` admits her even if the org blocks `example.com`.

One rule catches most people out: **if an allow list for the direction has any entries at any scanned scope, a sender or recipient that matches nothing is treated as blocked** (with the reason `not in allow list`). Adding a single entry to an org-level `receive` allow list therefore flips every inbox in the org from "accept by default" to "reject by default" for new inbound mail.

On unprefixed paths like `/v0/lists/...`, the scope comes from your API key: an org key manages org lists, a pod key manages that pod's lists, an inbox key that inbox's lists. The `/pods/{pod_id}/...` and `/inboxes/{inbox_id}/...` variants name the scope explicitly.

## Add and remove entries

Add an entry with the direction, type, and the address or domain. AgentMail derives the entry type itself: anything containing `@` is an email, anything else is a domain. A `reason` (up to 1,024 characters) is optional and shows up when the entry later blocks something.

<CodeGroup>

```python Python
from agentmail import AgentMail

client = AgentMail()  # reads AGENTMAIL_API_KEY

# Org scope: only accept new inbound mail from your company
client.lists.create("receive", "allow", entry="yourcompany.com")

# Inbox scope: block one sender for a single inbox
client.inboxes.lists.create(
    "agent@yourdomain.com", "receive", "block",
    entry="noise@example.com", reason="automated newsletter",
)
```

```typescript TypeScript
import { AgentMailClient } from "agentmail";

const client = new AgentMailClient({ apiKey: process.env.AGENTMAIL_API_KEY });

// Org scope: only accept new inbound mail from your company
await client.lists.create("receive", "allow", { entry: "yourcompany.com" });

// Inbox scope: block one sender for a single inbox
await client.inboxes.lists.create("agent@yourdomain.com", "receive", "block", {
  entry: "noise@example.com",
  reason: "automated newsletter",
});
```

```bash CLI
# Org scope: only accept new inbound mail from your company
agentmail lists create \
  --direction receive \
  --type allow \
  --entry yourcompany.com

# Inbox scope: block one sender for a single inbox
agentmail inboxes:lists create \
  --inbox-id agent@yourdomain.com \
  --direction receive \
  --type block \
  --entry noise@example.com \
  --reason "automated newsletter"
```

```bash curl
curl -X POST "https://api.agentmail.to/v0/lists/receive/allow" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"entry": "yourcompany.com"}'
```

</CodeGroup>

Removing an entry is a delete on the same path. Deletion returns `204` and takes effect on the next send or delivery.

<CodeGroup>

```python Python
client.lists.delete("receive", "block", entry="noise@example.com")
```

```typescript TypeScript
await client.lists.delete("receive", "block", "noise@example.com");
```

```bash CLI
agentmail lists delete \
  --direction receive \
  --type block \
  --entry noise@example.com
```

```bash curl
curl -X DELETE "https://api.agentmail.to/v0/lists/receive/block/noise@example.com" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY"
```

</CodeGroup>

Reading lists works with any key, but creating and deleting entries requires a verified organization.

## What happens to filtered mail

The two directions fail differently, and the difference is deliberate.

**Inbound** mail from a blocked sender is not bounced or dropped. It is delivered with a `blocked` label and hidden: message and thread listings exclude `blocked` (along with `spam`, `unauthenticated`, and `trash`) by default. To audit what got filtered, pass `include_blocked=true` when listing; your key also needs the `label_blocked_read` permission. The same mechanism handles the other two inbound classifications:

- `spam`: the message failed the spam verdict on delivery.
- `unauthenticated`: the message arrived with no SPF, DKIM, or DMARC headers at all. Mail whose auth headers are present but *failing* is dropped before delivery and cannot be recovered.

**Outbound** sends fail loudly. If any recipient matches a `send` block list (or misses a populated `send` allow list), the send returns `403 MessageRejectedError` naming each blocked recipient and the entry's reason, and nothing is sent.

## Automatic blocks

AgentMail also writes `send` block entries itself, at the org scope, in response to delivery feedback:

| Trigger | Entry `reason` | Deletable via API |
| --- | --- | --- |
| Permanent bounce | `bounced` | Yes |
| Spam complaint | `complained` | No (read-only) |
| List-Unsubscribe click | `Unsubscribed via List-Unsubscribe` | No (read-only) |

Only permanent bounces create entries. A transient bounce (a remote server temporarily deferring mail) does not block the address, because the recipient is real and future sends should succeed.

Complaint and unsubscribe entries are read-only because the recipient asked to stop hearing from you; re-enabling those sends programmatically would damage your sender reputation. Attempting to delete one returns `409 CannotDeleteError`.

## Unblock a recipient

If an address bounced once (a typo you fixed, a mailbox that was full) and you need to send to it again, delete its auto-created entry from the org send block list:

<CodeGroup>

```python Python
client.lists.delete("send", "block", entry="user@example.com")
```

```typescript TypeScript
await client.lists.delete("send", "block", "user@example.com");
```

```bash CLI
agentmail lists delete \
  --direction send \
  --type block \
  --entry user@example.com
```

```bash curl
curl -X DELETE "https://api.agentmail.to/v0/lists/send/block/user@example.com" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY"
```

</CodeGroup>

That clears AgentMail's own block, which is the whole story for custom-domain sending. Sends from the shared `agentmail.to` domain have a second layer: an account-level suppression list at the email provider (Amazon SES) that is populated automatically on bounce and complaint feedback, and on unsubscribe clicks. Deleting the AgentMail entry does not clear that layer, so shared-domain sends to the address can still be suppressed.

<Note>
Clearing SES-level suppression is support-only today. If a shared-domain recipient stays unreachable after you delete the block entry, contact [support@agentmail.cc](mailto:support@agentmail.cc). Sending from a custom domain avoids the shared suppression list entirely.
</Note>
