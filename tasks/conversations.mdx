Every message in AgentMail belongs to a thread: replies are attached server-side via the `in_reply_to` field, so a back-and-forth conversation stays one resource you can fetch, label, and search as a unit. This page covers reading threads, using labels to track what your agent has done, finding conversations with full-text search, and handling the 409 you get when concurrent writes touch the same thread.

All requests use `https://api.agentmail.to/v0` with `Authorization: Bearer $AGENTMAIL_API_KEY`.

## Fetch a thread

`GET /threads/{thread_id}` returns the thread's metadata and every message in it. Messages are ordered by `timestamp` ascending, so `messages[0]` is the oldest and the last element is the newest. If you only need the newest message, the metadata already points at it via `last_message_id`.

<CodeGroup>

```python Python
import os

from agentmail import AgentMail

client = AgentMail(api_key=os.environ["AGENTMAIL_API_KEY"])

thread = client.threads.get(thread_id=thread_id)

print(thread.subject)
print(thread.messages[-1].text)  # newest message
```

```typescript TypeScript
import { AgentMailClient } from "agentmail";

const client = new AgentMailClient({ apiKey: process.env.AGENTMAIL_API_KEY });

const thread = await client.threads.get(threadId);

console.log(thread.subject);
console.log(thread.messages.at(-1)?.text); // newest message
```

```bash curl
curl "https://api.agentmail.to/v0/threads/$THREAD_ID" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY"
```

</CodeGroup>

The metadata summarizes the whole conversation, so you rarely need to walk `messages` for bookkeeping:

| Field | Meaning |
| --- | --- |
| `labels` | Union of the labels on every message in the thread |
| `senders`, `recipients` | Every address that appears in the thread, as `username@domain.com` or `Display Name <username@domain.com>` |
| `subject`, `preview` | Subject, and a text preview of the last message |
| `timestamp` | Timestamp of the last sent or received message |
| `received_timestamp`, `sent_timestamp` | Timestamps of the last received and last sent message |
| `message_count`, `size` | Number of messages, and thread size in bytes |
| `last_message_id` | ID of the newest message |

To list threads instead of fetching one, `GET /threads` returns them newest-first with `count`, an optional `next_page_token` for paging, and a `labels` query parameter for filtering. The unprefixed path resolves its scope from your API key; `GET /inboxes/{inbox_id}/threads` and `GET /pods/{pod_id}/threads` pin the scope explicitly. List endpoints also accept `senders`, `recipients`, and `subject` substring filters, but filtered requests are served by search and cap `limit` at 100.

The same thread is browsable in the [console](https://console.agentmail.to) — sent and received messages interleaved in order, with the thread's labels on top:

## Track agent state with labels

Labels come in two kinds. System labels are set by the delivery pipeline and cannot be added or removed through the API: `received`, `sent`, `bounced`, `complained`, `delayed`, `delivered`, `rejected`, `opened`, and `scheduled`. Everything else is a custom label you own, which makes labels the natural place to record agent state on a conversation: mark a thread `triaged` after classification, `escalated` when a human takes over, then filter your work queue with the `labels` parameter on list endpoints.

`PATCH /threads/{thread_id}` takes `add_labels` and `remove_labels`. The change applies to every message in the thread, which keeps the invariant that a thread's `labels` field is the union of its messages' labels. A common loop: process new mail by listing threads with `labels=unread`, then remove `unread` and add your own state label in one call.

<CodeGroup>

```python Python
updated = client.threads.update(
    thread_id=thread_id,
    add_labels=["triaged"],
    remove_labels=["unread"],
)

print(updated.labels)
```

```typescript TypeScript
const updated = await client.threads.update(threadId, {
  addLabels: ["triaged"],
  removeLabels: ["unread"],
});

console.log(updated.labels);
```

```bash curl
curl -X PATCH "https://api.agentmail.to/v0/threads/$THREAD_ID" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"add_labels": ["triaged"], "remove_labels": ["unread"]}'
```

</CodeGroup>

Rules that apply to custom labels:

- Labels are trimmed and lowercased on write, and each label is capped at 256 characters.
- Passing a system label in `add_labels` or `remove_labels` returns a 400 `ValidationError`.
- If the same label appears in both `add_labels` and `remove_labels`, the removal wins.
- Thread updates are rejected with a 422 `UnprocessableError` once a thread has 100 or more messages. For threads that large, update messages individually with `PATCH /inboxes/{inbox_id}/messages/{message_id}`, or in groups of up to 50 with `POST /inboxes/{inbox_id}/messages/batch-update`.

## Search conversations

When you don't have a thread ID, thread search gives you relevance-ranked full-text search. The query is matched against senders, recipients, and subject as substrings, and against message bodies as tokenized full text. It is available at all three scopes:

| Scope | Endpoint |
| --- | --- |
| Organization | `GET /threads/search` |
| Pod | `GET /pods/{pod_id}/threads/search` |
| Inbox | `GET /inboxes/{inbox_id}/threads/search` |

<CodeGroup>

```python Python
results = client.threads.search(q="invoice 1042")

for thread in results.threads:
    print(thread.thread_id, thread.subject, thread.highlights)
```

```typescript TypeScript
const results = await client.threads.search({ q: "invoice 1042" });

for (const thread of results.threads) {
  console.log(thread.thread_id, thread.subject, thread.highlights);
}
```

```bash curl
curl -G "https://api.agentmail.to/v0/threads/search" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  --data-urlencode "q=invoice 1042"
```

</CodeGroup>

Results are ordered by relevance, best match first, not by recency. Each hit may carry a `highlights` object with the matched fragments per field (`from`, `recipients`, `subject`, `text`), matched terms wrapped in `**`; a field key is present only when the query matched that field, so the keys also tell you where the hit came from. `limit` defaults to 50 and cannot exceed 100, `page_token` pages through results, and `before`/`after` bound by time. Spam, trash, blocked, and unauthenticated threads are always excluded from search; there is no opt-in the way there is on list endpoints.

Message search exists at inbox scope only: `GET /inboxes/{inbox_id}/messages/search` behaves the same way but returns individual messages. There is no organization- or pod-scope message search. To find message content across inboxes, search threads at org scope and fetch the matching thread's messages.

Prefer list filters over search when you already know the sender or subject and want results by recency; prefer search when you're matching on body content or want the best match first.

## Handle concurrent updates

A thread has many writers: two replies can arrive at the same moment, and an inbound message can land while your label update is in flight. Every thread write is guarded optimistically, so instead of silently losing an update, the losing request fails with HTTP 409 and error name `RaceConditionError`.

Treat 409 as retryable: re-issue the same request. Because label updates are expressed as `add_labels`/`remove_labels` rather than a replacement list, replaying one converges to the state you asked for even if other writes landed in between. If your retry needs fresh data (for example, you branched on the thread's current labels), re-fetch the thread first, then re-apply.

**Fetch, label, and search AgentMail conversation threads**

Read a full email thread, track agent state with custom labels, and find conversations by full-text search. Use this when operating on existing mail rather than sending it.

## Do this

```bash
export AGENTMAIL_API_KEY="..."
BASE="https://api.agentmail.to/v0"

# Fetch a full thread (messages[] ordered by timestamp ascending, oldest first)
curl "$BASE/threads/$THREAD_ID" -H "Authorization: Bearer $AGENTMAIL_API_KEY"

# Update labels on every message in the thread
curl -X PATCH "$BASE/threads/$THREAD_ID" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"add_labels": ["triaged"], "remove_labels": ["unread"]}'

# Relevance-ranked full-text search across the organization
curl -G "$BASE/threads/search" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  --data-urlencode "q=invoice 1042"
```

## Facts

- Base URL: `https://api.agentmail.to/v0`; auth header `Authorization: Bearer $AGENTMAIL_API_KEY`.
- `GET /v0/threads/{thread_id}` returns thread metadata plus `messages[]` ordered by `timestamp` ascending (oldest first).
- Thread metadata fields: `inbox_id`, `thread_id`, `labels`, `timestamp`, `received_timestamp?`, `sent_timestamp?`, `senders`, `recipients`, `subject?`, `preview?`, `attachments?`, `last_message_id`, `message_count`, `size`, `updated_at`, `created_at`.
- A thread's `labels` is the union of the labels on its messages.
- `GET /v0/threads` lists threads ordered by `timestamp` descending; response is `{count, limit?, next_page_token?, threads[]}`; filter with `labels`, `before`, `after`; `senders`/`recipients`/`subject` substring filters are served by search and cap `limit` at 100.
- Scope: `/v0/threads...` resolves scope from the API key; `/v0/inboxes/{inbox_id}/threads...` and `/v0/pods/{pod_id}/threads...` set scope explicitly.
- System labels, set by the platform and rejected from `add_labels`/`remove_labels` with 400: `received`, `sent`, `bounced`, `complained`, `delayed`, `delivered`, `rejected`, `opened`, `scheduled`.
- Custom labels are trimmed and lowercased on write; maximum 256 characters per label.
- `PATCH /v0/threads/{thread_id}` body `{add_labels?, remove_labels?}` applies the change to every message in the thread; `remove_labels` wins on duplicates; response `{thread_id, labels}`.
- `PATCH /v0/threads/{thread_id}` returns 422 `UnprocessableError` when the thread has 100 or more messages; use `PATCH /v0/inboxes/{inbox_id}/messages/{message_id}` or `POST /v0/inboxes/{inbox_id}/messages/batch-update` (max 50 ids, atomic) instead.
- Thread search endpoints: `GET /v0/threads/search` (org), `GET /v0/pods/{pod_id}/threads/search`, `GET /v0/inboxes/{inbox_id}/threads/search`; query params `q`, `limit`, `page_token`, `before`, `after`.
- Message search endpoint: `GET /v0/inboxes/{inbox_id}/messages/search` (inbox scope only).
- Search matches `q` against senders, recipients, subject (substring) and message body (tokenized full text); results ordered by relevance, best match first.
- Search `limit` defaults to 50, maximum 100; paging via `page_token` stops within the first 10,000 results.
- Search results may include `highlights` with per-field matched fragments (`from`, `recipients`, `subject`, `text`), matched terms wrapped in `**`; a field key is present only when that field matched.
- Search always excludes spam, trash, blocked, and unauthenticated mail.
- Search and thread reads require the `message_read` permission; label updates require `message_update`.
- Concurrent writes to a thread (simultaneous inbound messages, racing label edits) fail with 409 `RaceConditionError`; retry the same request.

## Not supported

- No organization- or pod-scope message search: `GET /v0/messages/search` and `GET /v0/pods/{pod_id}/messages/search` do not exist. Search threads at org scope instead.
- System labels cannot be added or removed via the API.
- Search endpoints have no `include_spam`/`include_blocked`/`include_unauthenticated`/`include_trash` parameters; the exclusion is unconditional (list endpoints do accept them).
- No label rename operation: remove the old label and add the new one.
- Search results cannot be sorted by recency; use list endpoints with filters for recency ordering.

## Errors

| Error name | HTTP | Cause | Fix |
| --- | --- | --- | --- |
| `ValidationError` | 400 | System label in `add_labels`/`remove_labels`, or `limit` > 100 on search | Use custom labels only; keep `limit` at 100 or less |
| `ForbiddenError` | 403 | API key lacks `message_read` (reads/search) or `message_update` (label edits) | Use a key with the required permission |
| `NotFoundError` | 404 | Thread ID does not exist or is outside the key's scope | Check the ID and the key's inbox/pod/org scope |
| `RaceConditionError` | 409 | Concurrent write to the same thread raced this request | Retry the request |
| `UnprocessableError` | 422 | `PATCH /v0/threads/{thread_id}` on a thread with 100+ messages | Update messages individually or via batch-update |

## Verify

```bash
curl -G "https://api.agentmail.to/v0/threads" \
  -H "Authorization: Bearer $AGENTMAIL_API_KEY" \
  --data-urlencode "limit=1"
```

Success returns HTTP 200 with `{"count": ..., "threads": [...]}`. A thread object in the array confirms scope and `message_read` permission.
